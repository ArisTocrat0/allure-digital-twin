# ALLUR check in — C++ / SQLite / RU · KK · EN

**Decision-support digital twin for automotive production.**

Production Data → Digital Twin → Risk Detection → Root Cause → What-if Simulation → Recommendation → Business Impact

Основной путь демонстрации: **Дашборд → открыть главный риск → Найти решение → Сравнить сценарий**. В меню пять разделов: Дашборд, Производство, Сценарии, Риски и рекомендации, Настройки. KPI и риски рассчитываются существующим C++ ядром. Исходные тестовые таблицы кейса доступны в Настройках и сохраняются отдельно от параметров симуляции.

Текущий MVP работает на **синтетических данных**. Для промышленного внедрения нужны интеграция с MES/ERP/телеметрией, калибровка и проверка на реальных сменах ALLUR.

«Найти решение» проверяет до семи допустимых изменений: оператор, ускорение каждого участка на 10%, перенос первой поставки на срок до 50 минут, увеличение буферов. До трёх лучших вариантов ранжируются по заказам в срок, отгрузкам, выпуску, браку и времени ожидания. Варианты с ухудшением сроков или отгрузок не рекомендуются; без выявленной проблемы рекомендации не создаются. План автоматически не меняется.

Риски определяются по текущим состояниям и прогнозу до конца смены. Числовая вероятность в обычном детерминированном расчёте отсутствует; её не заменяют вымышленным процентом. Цепочка показывает наблюдения модели, а не доказанную отдельную причинность. What-if позволяет проверить эффект конкретного вмешательства.

Варианты пересчитывают **всю смену с начала**, а не продолжают текущий снимок; это ограничение существующего ядра. «Общий простой» — сумма времени ожидания и ремонта станций, не длительность остановки всего завода. Monte Carlo, ML, финансовый анализ и независимые линии сохранены в расширенном анализе; AI раскрывается отдельно. Шесть независимых линий не имеют общих распределяемых работников, материалов и оборудования.

Локальный прототип цифрового двойника автомобильной линии для QOSTANAI AI INDUSTRY HACKATHON 2026. Главный обзор использует тестовые таблицы с предоставленной страницы кейса. Симулятор использует отдельные синтетические параметры. **Модель не калибрована на ALLUR и не подключена к реальному заводу.** Сверка и ограничения исходных данных: [docs/case-data-audit.txt](docs/case-data-audit.txt).

## Что работает

- Дискретно-событийное C++17 ядро, эталонная реализация JS, воспроизводимые seed и фиксированный порядок событий.
- Три единичных станка, ограниченные буферы, атомарный BOM, поставки, операторы/смены, поломки/ремонт, контроль, одна переделка/брак, заказы/частичные отгрузки.
- Пять основных разделов; оборудование, ресурсы, история, тестовые таблицы и профиль встроены в них. Старые маршруты остаются доступны. Основные и расширенные параметры разделены; технические настройки по умолчанию свёрнуты.
- Полные словари русского, казахского и английского интерфейса. Язык аккаунта сохраняется в БД; язык гостя — только предпочтение в localStorage. Переводы не прошли редактуру носителем казахского языка.
- Реальная SQLite БД проекта: пользователи, серверные сессии, сценарии, неизменяемые исторические результаты. Миграция применяется автоматически.
- Регистрация, вход/выход, изменение имени/языка/пароля. Scrypt с индивидуальной солью; случайные HttpOnly / SameSite=Strict сессии, в БД только хэши идентификаторов; CSRF, Origin/Host checks, лимиты запросов, проверки владельца записей.
- Пять шаблонов сценариев, редактирование циклов/seed/операторов/поставки, сохранение и сравнение с независимым исходным сценарием.

## Запуск на этом компьютере

Собранное приложение доступно только на `http://127.0.0.1:3000`. Создайте собственный локальный аккаунт: готового общего пароля нет. Email — локальный логин; письма не отправляются.

```powershell
cd C:\Users\Ergali\Documents\project\allure-digital-twin
node server.js
```

Требуется **Node.js 24+** (используется `node:sqlite`). Приложение не требует внешних npm-пакетов для запуска. Для UI-тестов установлен Playwright (версия закреплена в package-lock.json). Локальные Node.js 24.19.0 с npm, Zig 0.15.2 и браузер Chromium находятся в tools/. Для команд npm добавьте tools/node-v24.19.0-win-x64 в PATH текущего терминала; для Chromium задайте PLAYWRIGHT_BROWSERS_PATH на tools/playwright-browsers. Если Node отсутствует в обычном PATH, `scripts/start.ps1` также умеет находить уже установленный Codex Node runtime на этом компьютере.

## Сборка из исходников

Windows: используется переносимый Zig 0.15.2 как C++ compiler, установка в систему не требуется. Скрипт проверяет закреплённый SHA256 архива с официального [ziglang.org](https://ziglang.org/download/).

```powershell
.\scripts\setup-toolchain.ps1
node scripts/build.cjs
node server.js
```

На Linux/macOS нужен доступный C++17 compiler (`c++` либо переменная `CXX`); скачивать Windows toolchain не нужно. `node scripts/build.cjs` использует `-std=c++17 -O3 -DNDEBUG`. JSON-библиотека nlohmann 3.12.0 включена в исходники с MIT-лицензией.

Если npm доступен, эквиваленты: `npm run build`, `npm start`, `npm test`, `npm run benchmark`.

Для резервного копирования остановите сервер и скопируйте папку `data/`; не копируйте только sqlite-файл во время активной WAL-записи.

## Семантика и ограничения

- Время и ресурсы целые. Смена/ремонт/ожидание оператора сохраняют остаток обработки; ремонт идёт по календарному времени. Операторы универсальны, приоритет контроль → сборка → кузов, обработка допускает прерывание.
- BOM (1 кузов + 1 двигатель + 4 колеса) целиком расходуется при запуске. Выходной станок удерживает изделие, если следующий буфер полон. `starved` и `blocked` различаются.
- Порядок на общей отметке: накопить работу до границы; поставки, поломки, ремонт, смены; завершения/контроль и движение downstream-first; отгрузки; дедлайны. Порядок равных событий стабилен.
- На горизонте принимаются поставки, завершаются операции и отгрузки, но новые операции/переделки и списание BOM запрещены. Нужная переделка остаётся `pendingRework` в НЗП. Готово не равно отгружено, срок включительный.
- Изменение исходного объекта после создания модели не меняет очередь событий. Снимки независимы; результаты в SQLite сохраняют конфигурацию своего прогона даже после редактирования сценария.
- **Сценарии и шаги API пересчитываются от t=0. Runtime restore и ветвление из текущего состояния не реализованы.** История — результаты для просмотра/повторного расчёта, не сериализованный checkpoint очереди.
- **Monte Carlo и ML доступны на странице «Аналитика и прогноз».** Прогноз использует 20–200 прогонов, заданные разбросы циклов/поставок и вероятность дополнительной поломки. ML обучается по CSV истории с временным разделением 80/20, сравнением Brier и ограничением экстраполяции. Эти модели не калиброваны на данных ALLUR.
- Один тип автомобиля и фиксированный маршрут из трёх станций на линию. Можно рассчитывать до шести независимых линий с выделенными ресурсами; совместное распределение ресурсов не реализовано. Нет переналадок, квалификаций, затрат/энергии, внешней логистики и MES/ERP. Нет доступа к производственной БД ALLUR. SQLite хранит данные приложения, не реальные данные завода.
- Сервер рассчитан на локальную демонстрацию: loopback HTTP, без публичного deployment. Для сетевого production нужны HTTPS/Secure cookies, управляемые аккаунты/восстановление, аудит, резервное копирование, нагрузочные и независимые security-тесты. Текущие проверки не являются сертификацией безопасности или UX «10/10».

## Демонстрация

## Проверенные границы ввода после аудита P2

Все используемые целые поля проверяются до преобразования в C++ `int`/`uint32_t`; числа вне диапазонов, дроби, строки и boolean отклоняются. Публичный API строже CLI, который также поддерживает секундные ручные эталоны:

| Поле | HTTP API | Native CLI |
|---|---|---|
| seed | 0…4294967295 | так же |
| горизонт | 1…28800 с | 1…604800 с |
| циклы | 30…3600 с | 1…3600 с |
| период отгрузки | 300…604800 с | 1…604800 с |
| операторы / индекс станции | 1…3 / 0…2 | так же |
| ёмкость буфера | 1…20 | так же |
| начальные остатки / количество в поставке | 0…10000 | так же |
| BOM | 1…100 | так же |
| время поставки, поломки, дедлайна | 0…604800 с | так же |
| длительность ремонта | 1…86400 с | так же |
| границы смен | 0…604800 с, начало < конца, без пересечений | так же |
| количество заказа | 1…1000 | так же |

Поставок, поломок и заказов не больше 20; смен не больше 10; заказ минимум один. Native `until`/каждый `targets` — 0…горизонт, `repeat` — 1…10000; это benchmark/тестовые параметры, HTTP repeat не предоставляет. ID записей API — положительные безопасные JS integers. Вычисляемые суммы и времена при этих ограничениях остаются в int32.

HTTP body ограничен 64000 **байтами**, декодируется целиком строгим UTF-8; повреждённые последовательности отклоняются. Native stdout использует потоковый UTF-8 decoder. Сценарии без поставок используют начальный запас; UI сохраняет каждую из нескольких поставок, включая неизменённый состав компонентов.

Поддержанная проверка native UB: сборка Zig/Clang с `-O1 -g -fsanitize=undefined -fsanitize-trap=undefined`, затем native/boundary тесты с `NATIVE_TEST_EXE` на этот бинарник. ASan и длительный нагрузочный тест не выполнялись.

### Unicode конфигурации

Перед сохранением, обновлением и расчётом проверяются все строковые значения и ключи конфигурации: непарные UTF-16 high/low surrogate отклоняются как HTTP 400 `invalid_config`. Корректные пары, включая emoji, сохраняются без замены символов. Проверка также применяется к сохранённой конфигурации перед отправкой в native-процесс; существующие записи БД не исправляются и не удаляются автоматически.

## Аналитика и требования кейса

Полная проверка требований: docs/criteria-audit.txt. Архитектура: docs/architecture.txt. Готовая презентация: docs/output/ALLUR-check-in-MVP.pptx.

Редактор полного плана содержит заказы, смены, оборудование (циклы и буферы), запасы/BOM, поставки, поломки и качество. Импорт/экспорт плана JSON, заказов CSV. В docs/examples/ есть валидные шаблоны; файлы SYNTHETIC-history-* содержат искусственные данные исключительно для демонстрации обучения.

Маршрут проверки: зафиксировать исходный план → изменить и применить параметры → найти ограничения → ввести допущения прогноза и цены → рассчитать → скачать отчёт. Бизнес-эффект: прирост отгрузок × маржа + снижение брака × стоимость брака + снижение поздних заказов × штраф − дополнительные расходы. Окупаемость вычисляется только при положительном среднем эффекте. Финансовые исходные значения по умолчанию равны нулю.

ML CSV: date,cycle,operators,delay,demand,late либо failure. Признаки известны до смены; date уникальна; минимум 40 записей. cycle — самый длинный заданный цикл, delay — ожидание первой поставки от начала смены (секунды, 0–7200). Поздние 20% истории не используются для нормализации и обучения. Неподходящая модель или параметры вне диапазона обучения скрывают оценку текущего плана. Для нового сеанса историю загружают заново; модель можно скачать в JSON.

Дополнительная проверка: node tests/lab-ui.cjs (npm run test:analytics-ui). Прогноз не может выдавать риск по заказам со сроками за пределами горизонта. P05/P95 — модельные процентили; интервал Wilson характеризует неопределённость оценки доли, а не точность модели на реальном заводе.

Проверки нового пути: `npm run test:decision-ui`; исходных таблиц: `npm run test:factory-ui`. Unit/integration: `npm test`. Проверяются риски, приоритеты, рекомендации, сравнения C++ what-if, отсутствие рекомендаций без проблемы, авторизация/CSRF, RU/KK/EN и компоновка 1920×1080, 1366×768, 390×844.

В текущем меню: Производство → Сценарии → Риски и рекомендации → Статистика. Настройки и выход находятся под шестерёнкой сверху. Язык — значок глобуса; тема сохраняется в браузере.

Статистика: «Текущая смена» показывает симуляцию без календарной даты; «По дням» использует датированные таблицы кейса. Выбор периода применяется кнопкой «Показать». Экспорт Excel соответствует активному режиму и выбранному периоду: XLSX содержит показатели, строки по дням, работу линий и простои. Отсутствующее качество отмечается как отсутствие данных, а не нулевой брак.
