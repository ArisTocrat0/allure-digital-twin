Работающий локальный MVP для QOSTANAI AI INDUSTRY HACKATHON 2026, кейс ALLUR.
**Все данные синтетические. Модель не калибрована на реальном ALLUR и не подключена к телеметрии.** Название репозитория по запросу: `allure-digital-twin`.

## Запуск

Требуется Node.js >=20, внешние зависимости для приложения не нужны.

```powershell
cd C:\Users\Ergali\Documents\project\allure-digital-twin
npm start
```

Откройте http://127.0.0.1:3000. Сервер слушает только loopback. Можно также открыть `index.html` напрямую. Публичное развёртывание не выполняется.

```powershell
npm test
```

UI-проверка использует отдельно установленный Playwright и Microsoft Edge:

```powershell
$env:PLAYWRIGHT_MODULE='C:\Users\Ergali\.cache\codex-runtimes\codex-primary-runtime\dependencies\node\node_modules\playwright'
npm run test:ui
```

На другом компьютере можно установить Playwright локально (`npm install --no-save --package-lock=false playwright`) и иметь установленный Edge. UI-тест сам запускает и останавливает сервер на 127.0.0.1:3107. Скриншоты создаются в `artifacts/` (не включены в Git).

## Демонстрация за 3 минуты

1. Seed 2026, исходный сценарий: нажмите +15 минут, запустите и поставьте на паузу. Посмотрите остаток времени, буферы, причины ожидания и журнал.
2. Нажмите «До конца»: 28 готовых и отгруженных, один брак. A-101 закрыт в 05:00 при сроке 04:00; A-102 в срок 08:00.
3. Выберите задержку поставки +2 часа: состояние сбрасывается, сравнение идёт с новым независимым исходным прогоном на том же seed. До конца: 26 отгруженных, A-102 недопоставлен на 2.
4. Добавьте оператора: итог снова 28, но A-101 закрыт в срок 04:00. В таблице сравнения виден прирост числа заказов в срок.
5. Ускорьте поставку: A-101 закрыт в 03:00. Дополнительная поломка: 27 отгруженных, A-102 недопоставлен на 1.
6. Сброс и повторный прогон дают тот же результат. «Исходный / без изменений» даёт нулевые дельты.

Это результаты данного демонстрационного seed, а не обещание эффекта для завода.

## Модель и допущения

- Дискретно-событийное ядро `engine.js`; время, остатки, ёмкости и длительности — целые числа. Переход к ближайшему событию или завершению, без шага симуляции в одну секунду. UI только задаёт момент наблюдения.
- Одна модель автомобиля, три единичных станка: подготовка кузова 360 с, сборка 600 с, контроль 420 с. Буферы по два изделия; склад готовых не ограничен.
- На старте автомобиля атомарно списывается 1 кузов, 1 двигатель, 4 колеса. Комплект нужен полностью. Никаких отрицательных остатков или виртуального создания деталей. BOM резервируется сразу на весь автомобиль, а не на отдельных операциях.
- При заполненном выходном буфере обработанный автомобиль остаётся на станке и блокирует его. `blocked` отличается от `starved`, ожидания BOM и оператора.
- Два универсальных оператора, по одному на работающий станок. Детерминированный приоритет: контроль → сборка → кузов. Приоритет может прерывать обработку; остаток сохраняется. На заблокированном станке оператор не удерживается. Дополнительный оператор не добавляет станок и не меняет цикл.
- Смены [00:00,03:30) и [04:00,08:00). Вне смены обработка не идёт. Поломка сохраняет остаток; ремонт идёт по календарному времени, включая перерыв. Перекрывающиеся ремонты удерживают станок до наиболее позднего конца.
- Демонстрационная плановая поломка сборки в 02:50 на 30 мин. Дополнительный сценарий добавляет ещё поломку в 01:30 на 60 мин. Поломки фиксированы, не статистическая надёжность оборудования.
- Контроль: вероятность первой неудачи 0.12, после единственной переделки 0.15. Это входные демонстрационные параметры, не оценённые проценты риска опоздания. Переделка занимает полный цикл контроля; новые детали не расходуются. Повторная неудача означает окончательный брак без возврата компонентов; производство запускает замену, если хватает материалов/времени.
- Случайное качество привязано к seed, ID изделия и номеру попытки. Сценарии используют одинаковые исходные случайные исходы для сопоставимости, без общей изменяемой модели.
- Начальный запас: 12 кузовов, 8 двигателей, 48 колёс. В 02:00 поставка 20/24/80. Задержка переносит её на 04:00, ускорение на 01:00.
- Два заказа с начала горизонта: 12 шт. к 04:00 и 16 шт. к 08:00. FIFO по сроку, частичные отгрузки разрешены. Рейсы каждый час. Готовность не означает отгрузку. Отгрузка точно в срок считается своевременной. Горизонт конечный: незавершённые заказы остаются незавершёнными, дата будущего выполнения не выдумывается.
- Одновременные события: сначала накопление обработки до границы, затем поставки, поломки, завершения ремонтов, границы смен; затем передача завершённых изделий/контроль качества и распределение операторов downstream-first; затем отгрузки; затем проверка дедлайна. Равные события внутри типа идут по порядку создания. Завершение обработки ровно в момент поломки или конца смены уже выполнено и может передать изделие.
- Снимок `snapshot()` — независимое представление для UI, не формат сериализации внутренней очереди. Пауза сохраняет живую модель; `advance()` продолжает её. Смена сценария создаёт две новые независимые модели от t=0; это не вмешательство посреди текущего прогона.
- Диагностика показывает накопленные причины ожидания, базовые циклы и связь соседних станций; это не оптимизатор и не доказательство единственной причины. ML/Monte Carlo и вероятности опоздания не заявляются.

Не моделируются варианты автомобилей, переналадки, транспорт между цехами, квалификация операторов, энергопотребление, финансовая себестоимость, логистика вне склада и реальные MES/ERP. Для промышленного применения нужны данные, калибровка и валидация с производством.

## Проверки

`tests/engine.test.js`: 22 теста; ручной эталон (циклы 2/3/2, готовность t=7 и t=10), атомарный BOM, смена/ремонт, ремонт вне смены, блокировка, одна переделка и брак, дедлайн и отгрузка, одинаковый seed, no-change, независимость сценариев, chunked pause/resume, ограничение операторов, одновременные события и перекрывающиеся ремонты. Пакетный тест выполняет 40 seed × 5 сценариев.

На каждом переходе ядро проверяет:

- запущено = незавершённое производство + готовые на складе + отгружено + брак;
- остаток компонента = начальный + поставки − BOM × запущено;
- буферы не переполнены, работающих станков не больше операторов;
- готово всего = склад готовых + отгружено; дублирования изделий нет.

`tests/ui.cjs`: Edge headless, запуск/пауза, шаг, повторные клики до конца, пять сценариев, сброс, seed validation, нулевые дельты no-change, desktop/mobile, отсутствие JS-ошибок и горизонтального переполнения на 390px.

## Checkpoint: изоляция и терминальная граница

Конструктор строит все ресурсы и события только из своей глубокой копии конфигурации; payload очереди также копируется. Внешняя мутация deliveries/failures после создания модели не влияет на неё. Регрессии проверяют мутацию поставки, мутацию поломки с одиночным/пошаговым advance и мутацию возвращённого snapshot.

При t = horizon принимаются поставки, завершаются уже выполненные операции, передаются готовые изделия в доступный буфер, выполняются отгрузки и проверка дедлайна. Новые операции (включая переделки), возобновление работы и списание нового BOM запрещены. Все станции получают статус «Горизонт завершён». Неудачный контроль ровно на горизонте оставляет pendingRework в НЗП; счётчик начатых переделок не увеличивается.

UI QA действительно выполнена через отдельный Playwright + headless Microsoft Edge, не через Windows Computer Use. Проверены DOM, клики, пауза, повторный запуск, сценарии, сброс, seed, ошибки JS, responsive и скриншоты. Инструмент node_repl отсутствует, поэтому существующая пользовательская сессия браузера и вход GitHub через UI не проверялись. Runtime restore/ветвление текущего снимка, Monte Carlo и вероятностный риск опоздания пока не реализованы; сценарии начинаются с t=0.
